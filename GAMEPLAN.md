# Taskwright Game Plan

## Outcome

Finish Taskwright as a polished, defensible portfolio repository demonstrating practical AI-agent evaluation engineering. Deliver one coherent local experience where someone configuring a customer-support agent can define its requirements, test its behavior against controlled fictional sources and simulated tools, inspect failures, and compare configurations fairly.

The intended training outcome is a versioned agent configuration with measured evidence of how well it meets the user's requirements, including failures, regressions and uncertainty. Training here means iterating on instructions, tool setup or retrieval behavior; running exercises does not automatically teach the underlying model or change its weights.

Taskwright should connect the user's requirements to scenarios, grading criteria and inspectable results. The portfolio release is complete when:

- A user can define and review an agent brief: its purpose, supported tasks, source documents and policies, allowed tools, required or prohibited actions, uncertainty handling, and observable success criteria.
- Scenarios and grading criteria trace back to that brief. The user can inspect why a requirement matters and what evidence would show success or failure before running an experiment.
- A real agent runner completes support tasks using controlled document retrieval and simulated support actions, with bounded execution and visible failure states.
- Versioned scenarios, agent configurations, tool calls, responses, evaluator versions, and outcomes are retained in inspectable run records.
- Evaluations separately show supported customer advice, correct actions, and compliance with explicitly required processes. They inspect actual responses and traces, show evidence for each result, and distinguish pass, fail, uncertain, and execution error. Evaluators are tested against known correct, incorrect, and ambiguous examples.
- One clear interface journey connects the brief, frozen requirements, bounded runs, transcript inspection, evidence review, configuration comparison and export. Earlier experiment pages remain accessible as supporting evidence without forcing visitors to reconstruct the product from its development history.
- At least one complete baseline–change–retest experiment is recorded, including regressions and uncertainty. Improvement is a measured result to investigate, not a required outcome to manufacture.
- A reader can identify the tested configuration, the requirement version it targets, and evidence explaining which requirements it meets and where it remains unreliable. Reserved evaluation is not required to finish this portfolio release; the four reserved cases remain unexecuted.
- A readable repository, reproducible demo and detailed case study explain architecture, engineering decisions, attribution, results, evaluator limitations and platform overlap. Setup and saved-evidence replay work without provider credentials; fresh execution has explicit prerequisites and is labeled separately.
- A rehearsed walkthrough demonstrates the complete journey and at least one meaningful failure, with proportionate automated and browser verification. Known limitations are documented rather than hidden behind an aggregate score.

This project should demonstrate impressive practical AI engineering through substance, usability and honest evidence. A finished portfolio artifact is a valid outcome without a startup or commercial launch. It does not promise employment, establish customer demand or prove reliability outside the tasks tested. Once the release criteria above are met, stop feature expansion and prepare a publication decision; publication itself requires explicit authorization.

## Scope

Taskwright remains independent, previously discussed as RepLab, and is not part of RepSuite. Finish with the existing customer-support coverage: exact product identification, evidence retrieval, supported instructions, policy boundaries, clarification, and escalation.

Include a local workflow for defining and versioning an agent brief, mapping its requirements to scenarios and evaluations, running a baseline, inspecting failures, editing a candidate, and comparing results. The source and tool environment, replaceable agent adapters, recorded runs, comparison interface, and development/reserved evaluation separation support that workflow. Use the existing fictional support suite as the worked example. Any newly authored brief must define the user's desired behavior and the rubric used to evaluate it.

Keep the first authoring workflow focused on support tasks and the existing local simulation. It does not require automatic scenario generation, autonomous prompt optimization, production integrations, or support for every kind of agent. The existing reset and wrong-model exercises are development seeds, not a sufficient evaluation suite or private holdout set.

Remaining release work covers workflow consolidation, narrowly necessary correctness fixes, repository onboarding, evidence navigation, case study, demo rehearsal and verification. Pause additional scenario families, experiment pages and open-ended runner infrastructure. New experiments must resolve a specific release-blocking question; additional run counts alone do not improve the portfolio.

An external-agent integration, potentially using the OpenAI Agents API, is optional. Consider one bounded proof only if it demonstrates useful evaluation beyond the local runner and materially improves the demo. It is not a release dependency or authorization for a runtime migration. Keep any new execution backend separately versioned and preserve existing evidence.

Stop expanding the human-training curriculum. Preserve its demo and simulation records as historical prototypes and authoring material. Model-weight training, real customer operations, public deployment, and a broad general-purpose agent platform are outside the initial build. Prompt, tool, and retrieval changes can be tested without claiming that model weights were trained.

## Guardrails

- Keep the project ambitious and cohesive. Do not reduce completion to two scenarios and documentation or inflate scope with unrelated features.
- Use fictional customers, products, manuals, and policies. Actions affect only the simulated environment; no real messages, purchases, or account changes.
- Favor local storage and low operating cost. Keep an offline replay path for development, but clearly distinguish it from newly executed agent runs. Paid services and provider credentials are not assumed available.
- Put explicit run, time, tool-call, and output limits around agent execution. Record cancellations, timeouts, adapter failures, and unavailable cost data honestly.
- Grade actual behavior and outputs, not an agent's multiple-choice or self-reported score. Deterministic checks cover what they can establish; semantic judgments need calibrated evaluation and an uncertain/review-needed outcome.
- Every mandatory criterion must trace to an explicit user requirement or a documented prerequisite for performing the task correctly. Make required processes clear in the agent's task instructions without revealing reserved answers or evaluator labels. Do not reward unnecessary steps solely because the grader expects them.
- Keep advice quality, action correctness, and required-process compliance distinct. Explain any combined selection rule and its tradeoffs; a process failure is not automatically a factual error, and a fluent supported reply cannot excuse a prohibited action.
- Freeze the requirement brief and its grading contract before tuning. If either changes, version it and compare both configurations under the same new contract. Preserve prior grades and decisions; a changed evaluator or requirement is not evidence that the agent improved.
- Freeze scenario and evaluator versions for comparisons. Keep development feedback separate from withheld evaluation inputs; do not present already exposed cases as unseen or private. Repeated tuning against a holdout invalidates that claim.
- Show individual failures and regressions alongside aggregates. Report variation across repeated trials; never infer improvement from a single favorable run or require a positive result.
- Treat source content as data, not authority over runner controls. Keep secrets out of prompts, transcripts, exports, and browser storage.
- Lead current portfolio copy with Taskwright's purpose, decisions and Robert's direction. Use a brief AI-assistance development note rather than repeated tool credits; preserve detailed attribution in historical records. Keep AI-authored test material and AI grading disclosures explicit, and do not imply unaided implementation or personal validation that did not occur. Distinguish AI review, deterministic checks, and human judgments. Synthetic task results do not prove human learning or production reliability.
- Taskwright is the selected product name, replacing Trywise. Use Taskwright for display text and taskwright for lowercase technical identifiers. The workspace folder and working URLs remain unchanged. Preserve historical names and frozen artifacts exactly. No name, domain or trademark availability is established, and publication is not authorized by the rename.
- After each completed task, update current state and the next best move. Put detailed specifications and evidence in supporting documents.

## Strategy

The portfolio direction supersedes open-ended product expansion. The OpenAI Agents API launch prompted a reassessment: managed agent execution overlaps with our runner infrastructure, and OpenAI's evaluation tools also overlap with grading and comparison. Taskwright must explain that overlap candidly; generic agent execution or scoring is not a demonstrated differentiator. Sources: [Agents API announcement](https://openai.com/index/introducing-the-agents-api/) and [agent evaluation documentation](https://developers.openai.com/api/docs/guides/agent-evals).

The strongest portfolio story is the complete support-specific requirements-to-evidence workflow: explicit authority, realistic policy decisions, separate behavior and process checks, calibrated reply review, repeated comparisons, retained failures and reproducible records. These are engineering choices to demonstrate, not claims of unique technology or a validated market advantage. Synthetic agents can exercise the system; they do not establish that prospective users find it useful.

Finish in this order: consolidate the existing product journey and address only defects that obstruct it; package the evidence and case study; rehearse setup, replay and the demo; then assess readiness for a portfolio release. Do not keep expanding to compensate for platform competition. A positive configuration result, external integration, reserved-case evaluation and paying customers are not completion requirements.
